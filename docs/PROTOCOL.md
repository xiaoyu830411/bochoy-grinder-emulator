# CRYSTAL 磨豆机 BLE 通讯协议

> 适用范围：咖啡机上的 Decaid 插件通过 BLE 控制 CRYSTAL 磨豆机。
>
> 整理日期：2026-11-23 · 插件包版本：`0.2.0`（见 `crystal-grinder.reaplugin/manifest.json`）

本文区分三类信息：

- **插件实现**：可直接由当前仓库的 `plugin.js`、manifest 和测试核对。
- **固件记录**：来自项目初版协议文档所引用的 R1 文档、`bleRPM.cpp/.h` 和样机实测记录。
  这些原始文件不在当前仓库中，硬件联调或固件升级时应再次核对。
- **待确认**：现有代码和记录不足以定义，不能当作既定协议使用。

## 1. 通讯架构与边界

咖啡机屏幕里的 App/Skin **不直接收发 BLE 字节**，完整链路是：

```text
咖啡机 App / Skin
      │  HTTP / WebSocket（JSON、base64 由插件桥内部处理）
      ▼
Decaid + com.crystal.grinder 插件
      │  BLE GATT（每个值固定为 2 字节）
      ▼
CRYSTAL 磨豆机（ESP32-S3）
```

本文只规定 **Decaid 插件与磨豆机之间的 BLE 协议**。App 可用的 HTTP/WebSocket
接口见 `INTERFACE.md`（上游文档，未随本仓库发布）。咖啡机本体的萃取控制走另一套 machine 接口，
不属于磨豆机 BLE 协议。

协议没有自定义的“帧头 + 命令字 + 数据 + 校验”包格式：每次 GATT 读、写或通知只承载
一个 `uint16`。BLE 链路层自身的校验不等于应用层命令应答。

## 2. 广播、发现与连接

| 项目 | 约定 | 依据 |
|---|---|---|
| 广播名 | `CRYSTAL-` + 4 位大写十六进制 MAC 后缀，例如 `CRYSTAL-E57C` | 固件记录 |
| 名称生成 | `sprintf("CRYSTAL-%02X%02X", mac[4], mac[5])` | 固件记录 |
| 广播内容 | 设备名 + 主服务 UUID | 固件记录 |
| 广播间隔 | 100–200 ms | 固件记录 |
| 连接参数 | interval min 18.75 ms / max 37.5 ms；latency 0；supervision timeout 6 s | 固件记录 |
| 主服务 UUID | `7fa2d10c-12f3-4b9e-9d77-1a9b65432100` | 插件实现 |
| 扫描匹配 | 广播名以 `CRYSTAL-` 开头 | 插件实现 |
| 连接后校验 | 必须发现上述主服务，否则连接初始化失败 | 插件实现 |

**注意：广播名只用于发现，不是设备身份认证。** 连接后还必须核对服务 UUID；需要绑定
固定设备时，应由上层保存 Decaid 设备 ID/BLE 地址，不能只保存显示名称。

### 2.1 广播数据示例（格式示意，不是实机抓包）

BLE 广播/扫描响应由多个 AD Structure 组成，每个结构为：

```text
Length（1 字节）  AD Type（1 字节）  AD Data（Length - 1 字节）
```

`Length` 不包含自身，但包含后面的 AD Type。以下假设设备名使用 Complete Local Name
（`0x09`），服务列表使用 Complete List of 128-bit Service UUIDs（`0x07`）。现有资料没有
保留原始广播抓包，因此实际 AD Type，以及名称放在广播包还是扫描响应中，仍需抓包确认。

**例 1：设备名 `CRYSTAL-E57C`**

```text
0D 09 43 52 59 53 54 41 4C 2D 45 35 37 43
│  │  └────────────── 12 字节 ASCII 设备名 ──────────────┘
│  └─ AD Type = 0x09：Complete Local Name
└──── Length = 13 = 1 字节 AD Type + 12 字节名称
```

名称的 ASCII 对照为：`CRYSTAL-` = `43 52 59 53 54 41 4C 2D`，`E57C` =
`45 35 37 43`。

**例 2：128 位主服务 UUID**

```text
标准字符串：7fa2d10c-12f3-4b9e-9d77-1a9b65432100
AD Data：  00 21 43 65 9B 1A 77 9D 9E 4B F3 12 0C D1 A2 7F

完整 AD Structure：
11 07 00 21 43 65 9B 1A 77 9D 9E 4B F3 12 0C D1 A2 7F
│  │  └──────────── 16 字节 128-bit UUID ────────────────┘
│  └─ AD Type = 0x07：Complete List of 128-bit Service UUIDs
└──── Length = 17 = 1 字节 AD Type + 16 字节 UUID
```

128 位 UUID 在 BLE 广播中按低字节优先排列，所以上面的 AD Data 与标准 UUID 字符串的
16 个字节顺序相反。它与“特征值中的 `uint16` 使用大端”属于不同层面的约定，并不矛盾。

> **不要把上述两个结构直接拼成一个传统广播包。** 名称结构为 14 字节，服务结构为 18
> 字节，合计 32 字节，尚未计入 Flags，已经超过传统广播 31 字节数据上限。实际固件可能
> 将名称放在扫描响应中，或采用其他分包方式；本例只解释字节格式，不指定实际包布局。

扫描工具通常会把 AD Structure 解析成类似下面的逻辑结果；这是解析后的示意，不是空中
字节，也不是 Decaid HTTP 返回体：

```json
{
  "name": "CRYSTAL-E57C",
  "serviceUuids": ["7fa2d10c-12f3-4b9e-9d77-1a9b65432100"]
}
```

插件先根据 `name` 的 `CRYSTAL-` 前缀认领设备，连接后再通过服务发现确认上述 UUID。

## 3. GATT 服务与特征值

所有特征值都在主服务 `7fa2d10c-12f3-4b9e-9d77-1a9b65432100` 下。
方向以插件为中心：**写**是插件 → 磨豆机，**通知**是磨豆机 → 插件。

| 名称 | 完整特征值 UUID | 含义 | 有效值 | 插件实际使用 |
|---|---|---|---|---|
| `MT_RPM` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432101` | 电机转速设定/回报 | 0–1500 | 连接时读、必需订阅、带响应写 |
| `XD_RPM` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432102` | 下豆参数 | 0–150 | 连接时读、可选订阅、带响应写 |
| `BOOT_SIGN` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432103` | 启动项/动作命令 | 固件允许 0–10；仅 1–5 已定义 | 仅带响应写 |
| `SYS_STATE` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432104` | 系统状态 | 已定义 0、1 | 连接时读、必需订阅；不写 |
| `SERVO_ANGLE` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432105` | 当前研磨度 | 0–1500 | 连接时读、必需订阅；不写 |
| `TF_ANGLE` | `7fa2d10c-12f3-4b9e-9d77-1a9b65432106` | 目标研磨度 | 0–1500 | 连接时读、可选订阅、带响应写 |

### 3.1 属性差异

R1 将 `SYS_STATE`、`SERVO_ANGLE` 描述为 READ/NOTIFY；既有固件记录显示，六个特征都
注册了 `READ | WRITE | NOTIFY`。插件只按上表使用，**不要向 `SYS_STATE` 或
`SERVO_ANGLE` 写入状态/当前值**，也不要把固件暴露了 WRITE 属性理解为这些写入有定义。

“必需订阅”失败会使插件连接初始化失败；“可选订阅”失败只记录日志，连接仍可继续。
可选不代表协议上可随意省略，而是插件为兼容部分固件保留的降级路径。

## 4. 数据编码

### 4.1 BLE 空中数据

- 长度固定为 **2 字节**。
- 类型为 **无符号 16 位整数 `uint16`**。
- 字节序为 **大端**：高字节在前。
- 解码：`value = (data[0] << 8) | data[1]`。
- 编码：`data = [(value >> 8) & 0xFF, value & 0xFF]`。
- 读取和通知同样使用这两个字节，不使用 ASCII 十进制字符串。

| 十进制 | 十六进制 | BLE 字节顺序 | Decaid BLE 桥中的 base64 |
|---:|---:|---|---|
| 0 | `0x0000` | `00 00` | `AAA=` |
| 1 | `0x0001` | `00 01` | `AAE=` |
| 3 | `0x0003` | `00 03` | `AAM=` |
| 4 | `0x0004` | `00 04` | `AAQ=` |
| 5 | `0x0005` | `00 05` | `AAU=` |
| 150 | `0x0096` | `00 96` | `AJY=` |
| 830 | `0x033E` | `03 3E` | `Az4=` |
| 1200 | `0x04B0` | `04 B0` | `BLA=` |
| 1500 | `0x05DC` | `05 DC` | `Bdw=` |

**base64 只存在于 Decaid 插件桥的 API 参数中，不要把 base64 的 4 个 ASCII 字节直接
写入 BLE 特征。** 例如设置 1500 时，BLE 写入的是 `05 DC`，不是字符串 `Bdw=`。

### 4.2 一次完整的编码/解码示例

以研磨度 **830** 为例：

```text
十进制：     830
十六进制：   0x033E
高字节：     0x03
低字节：     0x3E
BLE Value： 03 3E
插件桥参数： base64(03 3E) = "Az4="
```

磨豆机返回 `"Az4="` 时，插件的解码过程为：

```text
Base64 解码："Az4=" → [0x03, 0x3E]
数值解码：  (0x03 << 8) | 0x3E
          = 768 + 62
          = 830
```

再对比两个常见错误：

| 数据 | 含义 | 是否正确 |
|---|---|---|
| `03 3E` | 830 的 2 字节大端编码，可直接作为 GATT Value | 正确 |
| `3E 03` | 小端排列，会被解析为 15875 | 错误 |
| `41 7A 34 3D` | 字符串 `Az4=` 的 ASCII 字节，不是本协议的 2 字节 Value | 错误 |
| `38 33 30` | 字符串 `830` 的 ASCII 字节 | 错误 |

### 4.3 非法写入（固件记录）

- 写入长度不等于 2：固件不采用该值，将当前值回写到特征值并返回，不发送通知。
- 写入值超出特征范围：固件忽略该值，不回写、不通知。
- 这两种情况都不能依赖“一定会有通知”或“一定会有明确的应用层错误”来发现。

当前插件会在发送前校验研磨度、转速和下豆参数为范围内整数；第三方客户端也应先校验，
再回读或观察状态确认结果。

## 5. 命令定义

所有写命令均使用 **Write With Response（带响应写）**。GATT 写响应只说明写过程完成，
**不代表电机已经启动/停止，也不代表舵机已经到位**。

### 5.1 启动与停止：`BOOT_SIGN`

| 值 | BLE 字节 | 含义 | 当前 App/插件用法 |
|---:|---|---|---|
| 1 | `00 01` | 手动启动电机 | 手动模式开始 |
| 2 | `00 02` | 定时启动电机 | 定时模式开始；时长由磨豆机内部设置 |
| 3 | `00 03` | 智能启动（自动启停） | 默认开始方式 |
| 4 | `00 04` | 停止电机 | 停止按钮 / `stop()` |
| 5 | `00 05` | 应用目标研磨度 | 设置研磨度的第二步 |
| 0、6–10 | — | **未定义/保留** | 不要发送 |

`BOOT_SIGN` 在固件中是 Modbus 保持寄存器 `0x08` 的镜像，实际动作由磨豆机主控执行
（固件记录）。BLE 协议没有单独的“动作完成”应答命令。

**定时启动不携带时长。** 当前六个特征中没有 BLE 可写的定时时长；自动模式的触发量、
称重门槛或其他内部条件也不在这条 BLE 命令里。

**停止必须写 `BOOT_SIGN = 4`。不要把 `MT_RPM = 0` 当成等价的停止命令；协议没有定义
两者等价。**

### 5.2 设置研磨度：必须按顺序写两次

```text
插件                         磨豆机
  │  Write TF_ANGLE = value     │
  │────────────────────────────▶│
  │  Write With Response 完成    │
  │◀────────────────────────────│
  │  Write BOOT_SIGN = 5        │
  │────────────────────────────▶│
  │  Write With Response 完成    │
  │◀────────────────────────────│
  │       等待 SERVO_ANGLE 通知/回读确认 │
```

例如设置研磨度 830：

1. 向 `...65432106` 写入 `03 3E`（桥参数 `Az4=`）。
2. 上一步带响应写成功后，向 `...65432103` 写入 `00 05`（桥参数 `AAU=`）。

`TF_ANGLE` 是**目标值**，`SERVO_ANGLE` 是**当前值**。第一次写成功不等于当前研磨度
已经改变；第二次写成功也不等于机械结构已经到位。

> **两步操作不是事务。** 若第一步成功、第二步失败，可能只改变目标值而未应用。调用方应
> 保留未完成状态，重新读取 `TF_ANGLE` / `SERVO_ANGLE`，再决定补发 `BOOT_SIGN = 5`
> 或重发完整序列；不能向用户显示“已调整到位”。

插件对单次 `setGrindSetting()` 内的两次写进行顺序等待，但没有跨命令的全局写锁。
多个客户端或并发任务应自行串行化，避免另一个请求插入两次写之间。

### 5.3 设置电机转速：`MT_RPM`

- 向 `...65432101` 写入 0–1500 的整数。
- 示例：设置 1200，写入 `04 B0`（桥参数 `BLA=`）。
- 该值是设定/寄存器值，不应未经确认就解释为实时测得的刀盘转速。

### 5.4 设置下豆参数：`XD_RPM`

- 向 `...65432102` 写入 0–150 的整数。
- 示例：设置 88，写入 `00 58`（桥参数 `AFg=`）。
- 界面称其为“下豆”；其确切机械对象、单位，以及运行中修改何时生效，仍待厂家确认。

## 6. 状态读取与通知

### 6.1 系统状态

| `SYS_STATE` | 协议含义 | 插件快照 `state` |
|---:|---|---|
| 0 | 空闲 | `idle` |
| 1 | 研磨中 | `grinding` |
| 读取失败/尚未取得 | 非设备值，是客户端本地状态 | `unknown` |
| 2–65535 | **协议未定义** | 当前插件会按 `idle` 处理，见下方注意 |

> **实现限制：当前插件只特判 `1`，其他数值都会映射为 `idle`。新客户端不应复制这一
> 兜底行为；收到未定义值时应显示 `unknown`/故障待确认，而不是据此认定设备安全空闲。**
> 现有配方面板的 5 s 状态轮询也会把所有非 `grinding` 状态（包括 `unknown`）显示为
> `idle`，因此面板上的“空闲”目前不能用于安全联锁。

状态回到 `idle` 只能表示 `SYS_STATE = 0`。它是否必然代表电机完全停转、余粉排空或可以
立即开始萃取，协议没有进一步定义。

### 6.2 当前值与目标值

| 数据 | 来源 | 说明 |
|---|---|---|
| 当前研磨度 | `SERVO_ANGLE` | 发布为 Decaid 快照的 `setting` |
| 目标研磨度 | `TF_ANGLE` | 仅保存在插件会话中，不作为当前研磨度发布 |
| 电机转速值 | `MT_RPM` | 发布为快照的 `rpm` |
| 下豆值 | `XD_RPM` | 通过插件厂商接口的 `feed` 暴露 |

### 6.3 通知去重与兜底同步（固件记录）

- 固件按特征做去重：值不变时不重复通知。
- 固件每约 1 s 执行 `syncModbusToBle()` 同步寄存器与 BLE 值；这不等于每秒必定推送一次
  通知，因为未变化的值仍会被去重。
- 重新连接时，固件 `onConnect` 会重置通知去重缓存。
- 写入相同值后可能没有通知；可选订阅也可能失败。因此客户端必须在连接初始化时主动读取，
  并在需要确认时回读，不能只等待通知。

通知和初始读取可能相邻到达，客户端应允许重复快照，并始终按 2 字节大端解析；长度不等于
2 的数据应丢弃并记录，不能按 0 处理。

## 7. 插件连接初始化时序

当前插件的实际顺序如下（先订阅，再读取）：

1. 建立 GATT 会话，注册断连回调。
2. 发现服务；缺少 CRYSTAL 主服务则失败并清空会话。
3. 依次订阅必需特征：`SYS_STATE` → `SERVO_ANGLE` → `MT_RPM`。
4. 尝试订阅可选特征：`TF_ANGLE` → `XD_RPM`；失败仅记录日志。
5. 依次主动读取：`SYS_STATE` → `SERVO_ANGLE` → `TF_ANGLE` → `MT_RPM` → `XD_RPM`。
6. 每个初始读取独立容错；失败不会中止整个连接，但相应快照字段会缺失，状态可能为
   `unknown`。
7. 发布首个快照。首个快照发布失败会使连接初始化失败。
8. 后续由通知更新快照；`BOOT_SIGN` 不做初始读取，也不订阅。

断连后插件清空活动会话，后续命令报“未连接”；在没有新会话时，迟到的通知不再发布。
插件本身没有实现 BLE 自动重连、重试退避或断线自动补发命令；这些行为若存在，应由 Decaid
主机或上层 App 提供。WebSocket 自动重连不等于 BLE 已重新连接。

## 8. App 推荐控制时序

当前配方面板的单次 `pushAll()` 按以下顺序下发完整参数：

```text
设置研磨度（TF_ANGLE → BOOT_SIGN=5）
  → 设置 MT_RPM
  → 设置 XD_RPM
  → 用户单独触发 START（BOOT_SIGN=1/2/3）
```

任一步失败都会中断当前这次 `pushAll()`，之前已经成功的写入不会自动回滚。切换到绑定的
咖啡配方时会自动下发参数，但这段代码**不会自动启动电机**。

> **当前面板的提前解锁风险：**“调参完成即时研磨 = 是”的实际行为是保存后自动调用
> `pushAll()`，并非自动开始研磨；但保存路径在 `pushAll()` 完成前就把 `applied` 设为
> `true`，START 可能在参数仍写入时解锁。上层后续实现应等完整下发成功后再允许 START。

推荐上层遵循以下原则：

- 同一设备的所有写命令进入同一个串行队列，尤其是研磨度的两次写。
- “参数已发送”和“设备已就绪/已到位”使用不同状态，不把 HTTP 200 或 GATT 写响应当作后者。
- 开始研磨前检查有效连接和所需状态；未定义或未知状态不应被视为安全。
- 需要确认时，读取 `SERVO_ANGLE`、`MT_RPM`、`XD_RPM`、`SYS_STATE`，不要只等通知。
- 重连后重新读取完整状态，不沿用断线前的目标值或“已启动”状态。

## 9. 配对与安全

既有固件记录中的安全配置为：

```cpp
NimBLEDevice::setSecurityAuth(true, false, false); // bond=true, MITM=false, SC=false
// IO capability = NoInputNoOutput（Just Works）
```

但特征值没有设置 `READ_ENC` / `WRITE_ENC` 等加密访问要求。2026-10-23 的既有样机记录
（Windows 10/11、Decaid 0.9.1-beta.1、`CRYSTAL-E580`）表明：不在系统配对，也能扫描、
连接、读取状态和写入 `MT_RPM`。

因此当前实现口径是：

- **不要求预先配对，也不要求加密 GATT 访问。**
- 广播名前缀不是身份认证，协议中也没有应用层鉴权、命令序号或防重放机制。
- 不要把 BLE 控制接口当作安全边界；设备部署和现场访问应有相应物理约束。
- Just Works 不提供 MITM 身份验证。若未来固件强制加密/配对，Decaid 原生侧需要相应的
  `pair()` 能力，或调整固件访问策略，不能只修改这里的 2 字节编码。

## 10. 必须注意的风险与限制

1. **BLE STOP 不是紧急停止。** 插件没有证明断链时磨豆机会自动停止，也无法保证断链后还能
   送达 `BOOT_SIGN = 4`。固件是否有断联 watchdog/自动停机必须向厂家确认；人身安全不能
   依赖 App、WebSocket 或 BLE 停止按钮，应使用设备自身的停止/断电保护。
2. **没有应用层命令完成应答。** 写响应、HTTP 200、收到相同值通知都不能单独证明机械动作
   完成。需要到位保证时，应由厂家定义可验证的状态和超时策略。
3. **研磨度写入非原子且可并发交错。** 调用方必须串行化，并处理只写了一半的失败场景。
4. **去重意味着“没有通知”是正常情况。** 不能将其直接判为故障，也不能让命令 Promise 永久
   等待通知。
5. **未定义状态不能被当作空闲。** 当前插件对未知数值的 `idle` 映射是兼容性缺口，后续实现
   应改为显式未知；在那之前，上层对安全相关判断要格外保守。
6. **数值范围和物理单位不是一回事。** 0–1500 研磨刻度、0–1500 电机值、0–150 下豆值都不能
   自行换算成圈数、微米、rpm 或百分比。
7. **不要发送保留命令或写入只读语义的状态。** `BOOT_SIGN` 的 0、6–10，以及对
   `SYS_STATE` / `SERVO_ANGLE` 的写入，都没有已定义行为。
8. **部分成功不会回滚。** 完整配方包含至少四次 GATT 写（研磨度两次、转速一次、下豆一次），
   中途失败时设备可能处于新旧参数混合状态。

## 12. 请求、返回值与通知示例

以下示例用于说明格式，不是新的实机抓包。`C` 表示中央设备（Decaid 插件），`G` 表示
磨豆机。示例中的状态通知只有在校验/订阅成功且设备值发生变化时才可能出现。

### 12.1 GATT 请求与 ATT 空中数据的关系

在插件代码中，读写目标是 **Service UUID + Characteristic UUID**；在实际 ATT 数据包中，
后续读写使用的是连接建立后发现的 **Characteristic Value Handle**。不同固件、不同连接环境
不要共用写死的句柄，因此本文不伪造固定句柄字节。

| 操作 | ATT PDU 格式（示意） | 返回值 |
|---|---|---|
| Read Request | `0A <Handle>` | 无应用层请求 Value |
| Read Response | `0B <Value>` | 例如 `0B 03 3E`，响应值为 830 |
| Write Request（带响应写） | `12 <Handle> <Value>` | 例如写入自动启动时，Value 为 `00 03` |
| Write Response | `13` | **没有应用层 Value**，只表示 ATT 写响应成功 |
| Handle Value Notification | `1B <Handle> <Value>` | 例如状态通知 Value 为 `00 01` |

`Handle` 在 ATT 中占 2 字节并使用小端；本协议特征值的 `uint16` 则是大端，两者不要混淆。
抓包时还可能看到服务发现、CCCD 订阅配置等 ATT 请求，它们不属于上述 2 字节业务命令。

### 12.2 主动读取：请求没有 Value，响应携带 2 字节

读取 `SYS_STATE` 不需要再发送命令编号或数据体：

```js
var data = await gatt.read(SERVICE, CH.sysState);
// 示例返回 data = "AAA="，原始字节为 00 00
var value = decodeUint16(data); // 0，表示 idle
```

更多读取示例：

| 读取特征 | C 发出的 GATT 请求 | G 返回的原始 Value | 桥接返回值 | 解析结果 |
|---|---|---|---|---|
| `SYS_STATE ...0104` | Read，无 Value | `00 00` | `AAA=` | 0，空闲 |
| `SYS_STATE ...0104` | Read，无 Value | `00 01` | `AAE=` | 1，研磨中 |
| `SERVO_ANGLE ...0105` | Read，无 Value | `03 3E` | `Az4=` | 当前研磨度 830 |
| `TF_ANGLE ...0106` | Read，无 Value | `03 3E` | `Az4=` | 目标研磨度 830 |
| `MT_RPM ...0101` | Read，无 Value | `04 B0` | `BLA=` | 电机值 1200 |
| `XD_RPM ...0102` | Read，无 Value | `00 58` | `AFg=` | 下豆值 88 |

这里的“电机值 1200”只是寄存器数值，是否等于实时刀盘 rpm 仍按第 11 节待确认项处理。

### 12.3 自动启动与停止：写响应和状态通知是两件事

**自动启动示例：**

```text
C → G  Write With Response
       Characteristic = BOOT_SIGN (...65432103)
       Value = 00 03
       插件桥 data = "AAM="

G → C  Write Response
       成功，无应用层返回 Value；插件中的 Promise resolve

G → C  Notify SYS_STATE (...65432104)     【可能发生】
       Value = 00 01
       插件桥 data = "AAE="
       解析为 grinding
```

对应的插件桥写入形式：

```js
await gatt.writeWithResponse(SERVICE, CH.bootSign, "AAM=");
```

收到 Write Response 后，只能认为这次 GATT 写入完成。`SYS_STATE = 1` 的通知由主控后续
状态决定，不是 `BOOT_SIGN = 3` 的固定应答内容；没有收到通知时也不能直接推断启动失败。

**停止示例：**

```text
C → G  Write BOOT_SIGN = 00 04（桥 data = "AAQ="）
G → C  Write Response（成功，无应用层 Value）
G → C  Notify SYS_STATE = 00 00（桥 data = "AAA="）【若状态变为空闲】
```

### 12.4 设置研磨度 830：两个请求，各自有写响应

```text
第 1 步：写目标值
C → G  Write TF_ANGLE (...65432106)
       Value = 03 3E，桥 data = "Az4="
G → C  Write Response，成功，无应用层 Value

第 2 步：应用目标值
C → G  Write BOOT_SIGN (...65432103)
       Value = 00 05，桥 data = "AAU="
G → C  Write Response，成功，无应用层 Value

后续确认（不是固定的第三段命令应答）
G → C  Notify SERVO_ANGLE = 03 3E        【若值变化且订阅有效】
或
C → G  Read SERVO_ANGLE
G → C  Read Response Value = 03 3E        【示例：当前值已为 830】
```

插件中的对应调用为：

```js
await gatt.writeWithResponse(SERVICE, CH.targetAngle, "Az4=");
await gatt.writeWithResponse(SERVICE, CH.bootSign, "AAU=");

// 需要确认时主动读取；不能假设此时机械结构已经到位。
var current = await gatt.read(SERVICE, CH.servoAngle);
// 本例返回 "Az4="，解码为 830
```

即使最终读到 `SERVO_ANGLE = 830`，也只说明当前寄存器值；机械到位时序仍需厂家定义。

### 12.5 设置转速和下豆参数

| 操作 | C 发出的请求 | 原始 Value | 桥 data | 直接写响应 | 可能的后续通知 |
|---|---|---|---|---|---|
| 电机值设为 1200 | Write `MT_RPM ...0101` | `04 B0` | `BLA=` | 成功，无 Value | `MT_RPM = 04 B0`，若值变化且订阅有效 |
| 下豆值设为 88 | Write `XD_RPM ...0102` | `00 58` | `AFg=` | 成功，无 Value | `XD_RPM = 00 58`，若值变化且订阅有效 |

这里的“后续通知”仍是对应特征的独立 2 字节通知，不会把请求 ID、命令字或执行结果拼成
一个应用层应答包。

### 12.6 咖啡机 App 的 HTTP 请求与 JSON 返回示例

以下是 App/Skin 到 Decaid 的请求，不是直接发送给磨豆机的 BLE 数据。

**读取插件厂商状态接口：**

```http
GET /api/v1/plugins/com.crystal.grinder/status
```

连接时的返回示例：

```json
{
  "connected": true,
  "state": "idle",
  "setting": 830,
  "rpm": 900,
  "feed": 40
}
```

未连接时，当前插件返回 HTTP 200：

```json
{ "connected": false }
```

标准磨豆机快照接口则是：

```http
GET /api/v1/grinder/state
```

```json
{
  "timestamp": "2026-10-23T11:20:31.412Z",
  "state": "idle",
  "setting": "830",
  "rpm": 900
}
```

注意两个接口的 `setting` 类型不同：厂商 `status` 接口当前返回数字，标准快照中按 Decaid
约定返回字符串。

**自动启动：**

```http
POST /api/v1/plugins/com.crystal.grinder/start
Content-Type: application/json

{ "mode": "auto" }
```

BLE 写入成功时返回：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "mode": "auto", "sign": 3 }
```

其中 `sign: 3` 对应写入 `BOOT_SIGN` 的 `00 03`。HTTP 200 仍只表示写入调用完成，不是
“电机已经转起来”的凭证。

**设置下豆值：**

```http
POST /api/v1/plugins/com.crystal.grinder/feed
Content-Type: application/json

{ "feed": 88 }
```

```json
{ "feed": 88 }
```

**参数错误和断连返回示例：**

```text
POST /feed，body = {"feed":151}
→ HTTP 400
  {"error":"feed must be an integer 0-150"}

POST /start，body = {"mode":"auto"}，但磨豆机未连接
→ HTTP 503
  {"error":"grinder_not_connected"}

厂商 start/feed 写入时发生 BLE 错误
→ HTTP 502
  {"error":"<Decaid/BLE 错误文本>"}
```

标准 `/api/v1/grinder/setting`、`/rpm`、`/state/grinding` 和 `/state/idle` 的 HTTP 外层
状态由 Decaid 主机接口约定；它们分别映射到本文的 BLE 写序列，不应把外层成功响应扩展解释
为额外的磨豆机应用层应答。
